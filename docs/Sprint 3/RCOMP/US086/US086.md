# US086 — Pilot Remote Access

## 1. Context

This User Story is being developed for the first time in Sprint 3. It introduces a remote access mechanism allowing Pilots to interact with the AISafe system from outside the main application, over a TCP network connection.

The Pilot is responsible for several core user stories — **US081** (Import Flight Plan), **US082** (Insert Weather Data into a Flight Plan), and **US085** (Test/Validate a Flight Plan) — which were previously only accessible through the local backoffice console. US086 makes all of them remotely available through a dedicated TCP client application, without any direct database access from the client side.

This US follows the same architecture already established by **US044** (Weather Person Remote Access, port 2226) and **US078** (ATCC Collaborator Remote Access, port 2225).

---

## 2. Requirements

**US086** As a Pilot, I want to remotely access the system using the Air Transport Company App.

**Acceptance Criteria:**

- US086.1 — A specific **TCP-based network client application** is required to communicate with the server application embedded in the system.
- US086.2 — The client application interaction with the system must be **limited to the TCP connection**; any direct interaction with the database is unacceptable.
- US086.3 — **All Pilot user stories** (US081, US082, US085) must be remotely available using this client application.
- US086.4 — **Authentication and authorisation** must be enforced — only users with the `PILOT` role may use the service.

**Dependencies/References:**

- Depends on **US081** (Import Flight Plan) — must be remotely available; reuses `ImportFlightPlanController.importFromDsl()`.
- Depends on **US082** (Insert Weather Data) — must be remotely available; reuses `InsertWeatherDataController.insertWeatherDataByFlightId()`.
- Depends on **US085** (Test/Validate Flight Plan) — must be remotely available; reuses `TestFlightPlanController`.
- Referenced in the specification, section 6.6 (RCOMP Sprint 3).

## 3. Functioning

### 3.1 Overview

The Pilot TCP server is a standalone process that listens on a dedicated port (**2228**), separate from the ATCC server (port 2225) and the Weather Person server (port 2226). It shares the same PostgreSQL persistence unit as the rest of the system — the client never touches the database directly. Each incoming TCP connection is handled by a dedicated thread (`PilotClientHandler`), allowing multiple simultaneous Pilot sessions.

Authentication is enforced at the session level: no command other than `LOGIN` is accepted before the client has successfully authenticated with valid `PILOT` credentials.

**Pilot isolation** is enforced throughout: `LIST_DRAFT_PLANS`, `LIST_ALL_PLANS`, `INSERT_WEATHER`, and `TEST_FLIGHT_PLAN` all operate exclusively on flight plans belonging to the authenticated pilot, identified by their email address.

### 3.2 Protocol

The protocol is text-based, one command per line. Arguments are space-separated. **All server responses are multi-line and terminated by `END`** (or `BYE` for logout). This uniform termination allows the client to always read until `END`/`BYE` without needing to distinguish between single-line and multi-line responses.

**Commands:**

| Command | Arguments | Description |
|---|---|---|
| `LOGIN` | `<email> <password>` | Authenticate as a Pilot |
| `LIST_DRAFT_PLANS` | — | List all DRAFT flight plans belonging to this pilot |
| `LIST_ALL_PLANS` | — | List all flight plans for this pilot |
| `IMPORT_FLIGHT_PLAN` | — | Begin a DSL flight plan import session (US081) |
| `LIST_WEATHER_AREAS` | — | List all registered air control areas |
| `LIST_WEATHER_DATA` | `<areaCode>` | List available weather data for a given area |
| `INSERT_WEATHER` | `<flightPlanId> <weatherDataId>` | Associate weather data with a flight plan (US082) |
| `TEST_FLIGHT_PLAN` | `<flightPlanId>` | Test and validate a flight plan (US085) |
| `LOGOUT` | — | End the session |

**Response tokens:**

| Token | Meaning |
|---|---|
| `OK` | Command succeeded (first line of response) |
| `ERROR <reason>` | Command failed with explanation (first line of response) |
| `END` | Terminates every server response (including single-line ones) |
| `BYE` | Server acknowledges logout and closes the connection |

### 3.3 IMPORT_FLIGHT_PLAN Flow

The import command involves a multi-step exchange, since the `.fp` DSL file resides on the client's machine and must be transferred to the server:

```
Client → Server:  IMPORT_FLIGHT_PLAN
Server → Client:  OK Ready - send DSL lines then END_FILE
Client → Server:  <DSL line 1>
                  <DSL line 2>
                  ...
                  END_FILE
Server → Client:  (see response cases below)
```

**Response cases:**

**Success — new flight plan(s) imported:**
```
OK Flight plan(s) imported successfully:
  Flight ID : TP002
  Type      : regular
  Legs      : 2
    Leg 1   : OPO -> LIS  (fuel: 4500 kg)
    Leg 2   : LIS -> FAO  (fuel: 3000 kg)
  Status    : DRAFT
END
```

**Duplicate — flight plan ID already exists:**
```
ERROR Flight plan(s) already exist in the system:
  - TP010
  Use a different flight ID or delete the existing plan first.
END
```

**DSL syntax error:**
```
ERROR Invalid flight plan. Errors found:
  [SYNTACTIC] Line 13, Col 8 — mismatched input 'segment' expecting FUEL
END
```

**DSL semantic error:**
```
ERROR Invalid flight plan. Errors found:
  [SEMANTIC] Line 15, Col 8 — First segment of a leg must have phase 'climb' (got 'cruise')
  [SEMANTIC] Line 31, Col 8 — Last segment of a leg must have phase 'descent' (got 'climb')
END
```

The client reads the local `.fp` file automatically from disk — the user only specifies the file path. The server accumulates the received lines into a DSL string and passes it to `ImportFlightPlanController.importFromDsl()`, which runs the ANTLR parser and persists valid plans.

### 3.4 TEST_FLIGHT_PLAN Response

**PASS — flight plan is valid and feasible:**
```
OK PASS - Flight plan 'TP002' is valid and feasible
  Total distance   : 842 km
  Estimated flight : 1h 23min
  Declared fuel    : 7500 kg
  Estimated burn   : 5234 kg
  Remaining fuel   : 2266 kg
END
```

**FAIL — validation errors detected:**
```
ERROR FAIL:
  • Leg 1: combustivel declarado 500.0 kg abaixo do minimo estimado 6113.9 kg
  • Leg 1, Seg 1: altitude maxima 52000 ft excede o teto de servico da aeronave 41010 ft
END
```

The test runs a two-phase validation: (1) ANTLR DSL re-validation and (2) the C feasibility checker (`Scomp/bin/flight_plan_test`). On PASS, the flight plan status is updated to `TESTED`. On FAIL, it remains `DRAFT`.

### 3.5 INSERT_WEATHER Behaviour

The `INSERT_WEATHER` command accepts the **string flight plan ID** (e.g. `TP011`) rather than a numeric database ID, consistent with how all other commands reference flight plans. The server looks up the plan by flight ID internally.

If the flight plan is in `TESTED` status, inserting new weather data **reverts it to `DRAFT`**, since the previous test result is no longer valid with the updated weather conditions.

### 3.6 Session Lifecycle

| TCP Server Event | Behaviour |
|---|---|
| Client connects | Thread spawned, awaiting `LOGIN` |
| Authentication succeeds | Session marked authenticated; `OK Welcome <email>\nEND` sent |
| Authentication fails | `ERROR Invalid credentials\nEND` returned |
| Wrong role (not `PILOT`) | `ERROR Access denied: not a Pilot\nEND` returned |
| Command before login | `ERROR Not authenticated. Use: LOGIN <email> <password>\nEND` |
| Client sends `LOGOUT` | Session cleared; `BYE` sent; connection closed |
| TCP connection drops | Socket closed; thread exits |

### 3.7 Key Implementation Components

- **`PilotServer`** — standalone process. Configures `AuthzRegistry`, bootstraps default Pilot user, and accepts TCP connections on port 2228. Each connection spawns a `PilotClientHandler` daemon thread.
- **`PilotClientHandler`** — implements `Runnable`. Manages one client session: parses commands, enforces authentication, delegates to existing application-layer controllers. All responses are automatically terminated with `END` — single-line responses have it appended by the `run()` loop; multi-line responses include it explicitly.
- **`PilotClient`** — command-line TCP client. Connects to the server and reads user input in a loop. `IMPORT_FLIGHT_PLAN <path>` is intercepted locally: the client opens the `.fp` file, streams its lines to the server, and sends `END_FILE`. All other commands are forwarded as-is. `readResponse()` reads until `END` or `BYE`.
- **`Protocol`** — shared constants for all command and response tokens, used by all TCP servers (US044, US078, US086).
- **`ImportFlightPlanController.importFromDsl(String, String)`** — accepts DSL content as a string plus the pilot's email for ownership tracking.
- **`InsertWeatherDataController.insertWeatherDataByFlightId(String, Long)`** — looks up the flight plan by string ID before inserting weather data, consistent with the TCP command interface.

## 4. Integration/Demonstration

1. Start the **PilotServer**:
   ```
   bash pilot-server.sh
   ```
2. Start the **PilotClient** (in a second terminal):
   ```
   bash pilot-client.sh
   ```
3. Test authentication rejection — wrong password → `ERROR Invalid credentials` / `END`.
4. Authenticate successfully → `OK Welcome joao.silva@tap.pt` / `END`.
5. List all plans → `LIST_ALL_PLANS` → plan lines (flightId|type|status), terminated by `END`.
6. Import a flight plan → `IMPORT_FLIGHT_PLAN exemplo.core/flightplans/multi_leg_flight.fp` → success with details, or error list.
7. Import with syntax error → `IMPORT_FLIGHT_PLAN exemplo.core/flightplans/dsl_syntax_error.fp` → `ERROR Invalid flight plan. Errors found: ...` / `END`.
8. List weather areas → `LIST_WEATHER_AREAS` → area codes, terminated by `END`.
9. List weather data → `LIST_WEATHER_DATA LPPC` → records, terminated by `END`.
10. Insert weather data → `INSERT_WEATHER TP011 1` → `OK Weather data inserted into flight plan 'TP011'` / `END`.
11. Test a DRAFT plan → `TEST_FLIGHT_PLAN TP002` → PASS with statistics, or FAIL with error list.
12. Logout → `LOGOUT` → `BYE`.

## 5. Observations

- Port **2228** is dedicated to the Pilot service. The ATCC server (US078) uses port 2225 and the Weather Person server (US044) uses port 2226. All three run as independent processes on the same cloud node.
- The server shares the PostgreSQL persistence unit (`eapli.base.AlSafePU.postgres`) with the main application. The client has no database access whatsoever — all persistence is done server-side through the existing application-layer controllers.
- The C feasibility checker (`Scomp/bin/flight_plan_test`) must be compiled and accessible on the server node where `PilotServer` runs. It is invoked by `TestFlightPlanController` during the `TEST_FLIGHT_PLAN` command.
- The bootstrap mechanism in `PilotServer` is idempotent — if the default users already exist in the database, the bootstrap catches the exception silently and continues.
- US080 (Create Flight Plan manually) is not exposed via this TCP server in Sprint 3, as it requires interactive multi-step input that does not map cleanly to a single command line.
- **Pilot isolation**: all flight plan operations are scoped to the authenticated pilot's email. A pilot cannot list, test, or modify flight plans belonging to another pilot.
