# US090 — External Logging of Remote Accesses

## 1. Context

This User Story is being developed for the first time in Sprint 3. It introduces a cross-cutting logging mechanism for all remote access events in the AISafe system.

The three remote access services — **US44** (Weather Person), **US78** (Air Transport Company Collaborator), and **US86** (Pilot) — each operate TCP servers that authenticate users and serve requests. US090 adds a UDP-based side channel: every login attempt, successful login, logout, and disconnect is reported asynchronously to a dedicated **Remote Accesses Logging Server** running on a separate network node.

This US depends on US44, US78, and US86 being operational, as it hooks into their authentication and session lifecycle events.

---

## 2. Requirements

**US090** As Administrator, I want to have logs for every remote access to the system.

**Acceptance Criteria:**

- US090.1 — Remote access events must be transmitted to the Remote Accesses Logging Server using **UDP datagrams**.
- US090.2 — Both **successful logins** and **failed logins** must be registered.
- US090.3 — **Logouts** and **disconnects** must also be logged.
- US090.4 — Each logged event must include: **timestamp**, **username**, **client IP address**, **client port number**, and the **service identifier** (US44, US78, or US86).
- US090.5 — The Remote Accesses Logging Server must run on a **dedicated network node** (separate from the main application server).
- US090.6 — Logging must be **non-blocking** — a failure to deliver the UDP datagram must not interrupt the TCP server's normal operation.

**Dependencies/References:**

- Depends on **US44** (Weather Person remote access) — TCP server that must emit log events.
- Depends on **US78** (Air Transport Company Collaborator remote access) — TCP server that must emit log events.
- Depends on **US86** (Pilot remote access) — TCP server that must emit log events.
- Extended by **US91** (Remote accesses logging visualisation) — adds HTTP/AJAX front-end on top of the Logging Server.
- Referenced in the specification, section 6.6 (RCOMP Sprint 3).

## 3. Functioning

### 3.1 Overview

The Remote Accesses Logging Server is a standalone UDP server. It does not interact with the main EAPLI database — its sole responsibility is to receive, store, and expose access log entries. Each of the three TCP servers (US44, US78, US86) sends a UDP datagram to this server whenever a login, logout, or disconnect event occurs.

### 3.2 UDP Datagram Format

The payload is a UTF-8 encoded, pipe-separated string:

```
<eventType>|<service>|<timestamp>|<username>|<clientIp>|<clientPort>
```

Event types: `LOGIN_SUCCESS`, `LOGIN_FAIL`, `LOGOUT`, `DISCONNECT`

Examples:
```
LOGIN_SUCCESS|US86|2026-06-03T10:45:00|pilot@tap.pt|192.168.1.22|54321
LOGIN_FAIL|US44|2026-06-03T10:45:12|unknown|192.168.1.55|60011
LOGOUT|US78|2026-06-03T11:00:00|collab@ryanair.com|192.168.1.33|49152
DISCONNECT|US86|2026-06-03T11:05:30|pilot@tap.pt|192.168.1.22|54321
```

The format is intentionally simple to minimise datagram size and parsing complexity. No acknowledgement or retry is expected — UDP is best-effort by design.

### 3.3 Event Lifecycle

| TCP Server Event             | Log Event Type  |
|------------------------------|-----------------|
| Authentication succeeds      | `LOGIN_SUCCESS` |
| Authentication fails         | `LOGIN_FAIL`    |
| Client sends logout request  | `LOGOUT`        |
| TCP connection drops / reset | `DISCONNECT`    |

### 3.4 Network Architecture

The Remote Accesses Logging Server runs on a dedicated node (separate machine or container). The three TCP servers on the main application server each hold a reference to a `RemoteAccessLogger` utility that wraps a `DatagramSocket`. On each relevant event, the TCP server calls `logger.log(...)` which constructs the payload and fires the UDP datagram — non-blocking, exceptions silently caught.

The Logging Server binds to a configurable UDP port (default **9090**) and runs an infinite receive loop. Each received datagram is parsed into a log entry, appended to a log file (`remote_access_log.txt`) and added to an in-memory list (used by US91).

### 3.5 Key Implementation Components

- **`RemoteAccessLogger`** — UDP sender utility, used by US44, US78, and US86 TCP servers. Wraps `DatagramSocket.send()`. All exceptions are caught and silently swallowed to guarantee non-blocking behaviour.
- **`AccessLogEntry`** — immutable value object representing one log entry (eventType, service, timestamp, username, clientIp, clientPort). Has a `fromPayload(String)` factory method for parsing.
- **`EventType`** — enum with values `LOGIN_SUCCESS`, `LOGIN_FAIL`, `LOGOUT`, `DISCONNECT`.
- **`RemoteAccessesLoggingServer`** — standalone process. Binds UDP socket, runs receive loop, persists entries to file, exposes `getEntries()` (thread-safe, for US91).

## 4. Integration/Demonstration

1. Start the **Remote Accesses Logging Server** on its dedicated node: `java -jar remote-logging-server.jar`.
2. Start the main application server (US44, US78, US86 TCP servers active).
3. Connect with the Weather Person client (US44) → enter wrong password → `LOGIN_FAIL` entry appears in `remote_access_log.txt`.
4. Connect again → correct password → `LOGIN_SUCCESS` entry appears.
5. Perform an action → logout → `LOGOUT` entry appears.
6. Force-close the client → `DISCONNECT` entry appears.
7. Repeat for US78 and US86 clients to confirm all three services log correctly.

---

## 5. Observations

- UDP is inherently unreliable (datagrams may be lost). This is acceptable per the specification — logging is best-effort and non-critical to system correctness.
- The `RemoteAccessLogger` has no framework dependencies so it can be instantiated directly inside the RCOMP TCP server threads without coupling to the EAPLI application context.
- The log file produced by the Logging Server is the data source for US91's HTTP visualisation pages.
