# US044 — Weather Person Remote Access

## 1. Context

This User Story is being developed for the first time in Sprint 3. It introduces a remote access mechanism allowing Weather Persons to interact with the AISafe system from outside the main application, over a TCP network connection.

The Weather Person is responsible for three core user stories — **US041** (Register Weather Data), **US042** (Import Bulk Weather Data), and **US043** (Consult Weather Data) — which were previously only accessible through the local backoffice console. US044 makes all three remotely available through a dedicated TCP client application, without any direct database access from the client side.

This US is a dependency of **US090** (External Logging of Remote Accesses), which hooks into the authentication and session lifecycle events emitted by this TCP server.

---

## 2. Requirements

**US044** As a Weather Person, I want to remotely access the system in order to upload weather data.

**Acceptance Criteria:**

- US044.1 — A specific **TCP-based network client application** is required to communicate with the server application embedded in the system.
- US044.2 — The client application interaction with the system must be **limited to the TCP connection**; any direct interaction with the database is unacceptable.
- US044.3 — **All Weather Person user stories** (US041, US042, US043) must be remotely available using this client application.
- US044.4 — **Authentication and authorisation** must be enforced — only users with the `WEATHER_PERSON` role may use the service.

**Dependencies/References:**

- Depends on **US041** (Register Weather Data) — must be remotely available.
- Depends on **US042** (Import Bulk Weather Data) — must be remotely available.
- Depends on **US043** (Consult Weather Data) — must be remotely available.
- Extended by **US090** (External Logging of Remote Accesses) — adds UDP-based logging of login, logout, and disconnect events emitted by this server.
- Referenced in the specification, section 6.6 (RCOMP Sprint 3).

## 3. Functioning

### 3.1 Overview

The Weather Person TCP server is a standalone process that listens on a dedicated port (**2226**), separate from the ATCC server (port 2225). It shares the same PostgreSQL persistence unit as the rest of the system — the client never touches the database directly. Each incoming TCP connection is handled by a dedicated thread (`WeatherClientHandler`), allowing multiple simultaneous Weather Person sessions.

Authentication is enforced at the session level: no command other than `LOGIN` is accepted before the client has successfully authenticated with valid `WEATHER_PERSON` credentials. Security clearance expiry is also checked at login time.

### 3.2 Protocol

The protocol is text-based, one command per line. Arguments are space-separated. Date/time tokens use ISO format without spaces (`yyyy-MM-ddTHH:mm`) to avoid conflicts with the space delimiter.

**Commands:**

| Command | Arguments | Description |
|---|---|---|
| `LOGIN` | `<email> <password>` | Authenticate as a Weather Person |
| `LIST_AREAS` | — | List all registered air control areas |
| `REGISTER_WEATHER` | `<areaCode> <subMinLat> <subMaxLat> <subMinLon> <subMaxLon> <minAlt> <maxAlt> <startISO> <endISO> <windDir> <windSpeed>` | Register a single weather data record (US041) |
| `IMPORT_WEATHER` | — | Begin a bulk CSV import session (US042) |
| `CONSULT_WEATHER` | `<areaCode> <yyyy-MM-dd>` | Consult weather data for an area and date (US043) |
| `LOGOUT` | — | End the session |

**Response tokens:**

| Token | Meaning |
|---|---|
| `OK` | Command succeeded |
| `ERROR <reason>` | Command failed with explanation |
| `END` | Terminates a multi-line response |
| `BYE` | Server acknowledges logout and closes the connection |

### 3.3 IMPORT_WEATHER Flow

The bulk import command involves a multi-step exchange, since the CSV file resides on the client's machine and must be transferred to the server:

```
Client → Server:  IMPORT_WEATHER
Server → Client:  OK Ready - send CSV lines then END_FILE
Client → Server:  <header line>
                  <data line 1>
                  <data line 2>
                  ...
                  END_FILE
Server → Client:  OK imported=N rejected=M
                  ERROR <per-record error, if any>
                  END
```

The client reads the local CSV file automatically from disk — the user only specifies the file path. The server accumulates the received lines into a temporary file on the server's filesystem, passes its path to the existing `ImportBulkWeatherDataController`, and deletes the temporary file afterwards. This design reuses the existing controller without modification.

### 3.4 Session Lifecycle

| TCP Server Event | Behaviour |
|---|---|
| Client connects | Thread spawned, awaiting `LOGIN` |
| Authentication succeeds | Session marked authenticated; `LOGIN_SUCCESS` event emitted to US090 logger |
| Authentication fails | Error returned; `LOGIN_FAIL` event emitted to US090 logger |
| Security clearance expired | Login refused with specific message |
| Wrong role (not `WEATHER_PERSON`) | Login refused with access denied message |
| Client sends `LOGOUT` | Session cleared; `LOGOUT` event emitted; `BYE` sent; connection closed |
| TCP connection drops | `DISCONNECT` event emitted to US090 logger |

### 3.5 Key Implementation Components

- **`WeatherServer`** — standalone process. Configures `AuthzRegistry`, registers valid e-mail domains, bootstraps default users, and accepts TCP connections on port 2226. Each connection spawns a `WeatherClientHandler` daemon thread.
- **`WeatherClientHandler`** — implements `Runnable`. Manages one client session: parses commands, enforces authentication, delegates to existing application-layer controllers (`RegisterWeatherDataController`, `ImportBulkWeatherDataController`, `ConsultWeatherDataController`).
- **`WeatherClient`** — command-line TCP client. Connects to the server and reads user input in a loop. The `IMPORT_WEATHER` command is intercepted locally: the client opens the specified file, streams its lines to the server, and sends `END_FILE`. All other commands are forwarded to the server as-is.
- **`Protocol`** — shared constants for all command and response tokens, used by both ATCC (US78) and Weather Person (US44) servers.

## 4. Integration/Demonstration

1. Start the **WeatherServer** on the DEI cloud node:
   ```
   java -cp <fat-jar> rcomp.WeatherServer
   ```
2. On a local workstation, start the **WeatherClient** pointing to the server:
   ```
   java -cp <fat-jar> rcomp.WeatherClient <server-host> 2226
   ```
3. Test authentication rejection — enter wrong password → `ERROR Invalid credentials`.
4. Authenticate successfully → `OK Welcome weather@alsafe.com`.
5. List areas → `LIST_AREAS` → area codes returned, terminated by `END`.
6. Register a weather record → `REGISTER_WEATHER AREA1 38.5 39.0 -9.5 -8.5 0 5000 2026-06-05T10:00 2026-06-06T10:00 270.0 15.5` → `OK Weather data registered`.
7. Import a bulk CSV file → `IMPORT_WEATHER /path/to/weather.csv` → server processes and returns `OK imported=N rejected=M`.
8. Consult data → `CONSULT_WEATHER AREA1 2026-06-05` → matching records returned, terminated by `END`.
9. Logout → `LOGOUT` → `BYE`.
10. Force-close the client → confirm `DISCONNECT` event is logged by US090.

## 5. Observations

- Port **2226** is dedicated to the Weather Person service. The ATCC server (US78) uses port 2225. Both run as independent processes on the same cloud node, each with their own `ServerSocket`.
- The server shares the PostgreSQL persistence unit (`eapli.base.AlSafePU.postgres`) with the main application. The client has no database access whatsoever — all persistence is done server-side through the existing application-layer controllers.
- The `IMPORT_WEATHER` mechanism uses a server-side temporary file as an intermediary. This avoids modifying the existing `CsvWeatherDataReader` and `ImportBulkWeatherDataController`, which are designed to work with file paths. The temporary file is always deleted after processing, regardless of success or failure.
- UDP logging (US090) is integrated as a non-blocking side channel. Logging failures do not affect the TCP server's normal operation.
- The bootstrap mechanism in `WeatherServer` is idempotent — if the default users already exist in the database (created by the main application), the bootstrap catches the exception silently and continues.
