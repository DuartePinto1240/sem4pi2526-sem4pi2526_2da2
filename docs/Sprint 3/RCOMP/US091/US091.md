# US091 — Remote Accesses Logging Visualisation

## 1. Context

This User Story is being developed for the first time in Sprint 3. It extends **US090** (External Logging of Remote Accesses) by adding an HTTP front-end to the Remote Accesses Logging Server, allowing Administrators to view access logs from a standard web browser without requiring any dedicated client application.

The Remote Accesses Logging Server already receives and stores UDP log entries from the three TCP services (US44, US78, US86). US091 adds an HTTP server layer on top of this same process, exposing two dynamically updated pages — one for recent events and one for currently active users — using AJAX to avoid full page reloads.

This US depends on **US090** being operational, as it builds directly on top of the Logging Server infrastructure.

---

## 2. Requirements

**US091** As Administrator, I want to view the logs stored at the Remote Accesses Logging Server.

**Acceptance Criteria:**

- US091.1 — The Remote Accesses Logging Server application must contain an **HTTP server** to provide status pages to clients running a standard web browser.
- US091.2 — At least **two pages** must be available:
    - A page presenting the **list of the last recorded events**.
    - A page presenting the **list of remote users currently active**.
- US091.3 — Both pages must be **kept updated** to represent the current standing.
- US091.4 — **AJAX** must be used to update the presented data without the need of reloading the page.

**Dependencies/References:**

- Depends on **US090** (External Logging of Remote Accesses) — the Logging Server and its in-memory log store must be operational.
- Depends on **US44**, **US78**, **US86** — these TCP services generate the events that populate the log.
- Referenced in the specification, section 6.6 (RCOMP Sprint 3).

## 3. Functioning

### 3.1 Overview

The HTTP server runs inside the same process as the Remote Accesses Logging Server (US090). When the process starts, two threads are launched: the existing **UDP receive loop** (US090) and a new **HTTP listener** on port **8090**. Both share the same in-memory log store (`AccessLogStore`), which is thread-safe.

An Administrator opens a browser and navigates to `http://<logging-server-host>:8090/`. From there, two pages are available. Each page uses JavaScript `setInterval` to fire an AJAX request every 3 seconds, fetching fresh JSON data from a dedicated API endpoint and updating the DOM — no full page reload occurs.

### 3.2 Pages and Endpoints

| URL | Description |
|---|---|
| `/` or `/events` | HTML page — list of last recorded events |
| `/active` | HTML page — list of currently active remote users |
| `/api/events` | JSON API — returns the last N log entries |
| `/api/active` | JSON API — returns users with an open session (LOGIN_SUCCESS with no matching LOGOUT or DISCONNECT) |

### 3.3 JSON Response Formats

**`/api/events`** — array of log entries, most recent first:
```json
[
  {
    "eventType": "LOGIN_SUCCESS",
    "service": "US86",
    "timestamp": "2026-06-03T10:45:00",
    "username": "pilot@tap.pt",
    "clientIp": "192.168.1.22",
    "clientPort": 54321
  },
  {
    "eventType": "LOGIN_FAIL",
    "service": "US44",
    "timestamp": "2026-06-03T10:44:12",
    "username": "unknown",
    "clientIp": "192.168.1.55",
    "clientPort": 60011
  }
]
```

**`/api/active`** — array of currently active sessions:
```json
[
  {
    "username": "pilot@tap.pt",
    "service": "US86",
    "loginTime": "2026-06-03T10:45:00",
    "clientIp": "192.168.1.22",
    "clientPort": 54321
  },
  {
    "username": "collab@ryanair.com",
    "service": "US78",
    "loginTime": "2026-06-03T10:50:00",
    "clientIp": "192.168.1.33",
    "clientPort": 49152
  }
]
```

### 3.4 Active User Derivation

A user is considered **currently active** if:
- Their most recent event for a given `(username, service, clientIp, clientPort)` tuple is `LOGIN_SUCCESS`, and
- No subsequent `LOGOUT` or `DISCONNECT` event exists for the same tuple.

This derivation is computed by `AccessLogStore.getActiveSessions()` on each API request, scanning the in-memory list. No persistent session state is maintained — the derivation is always recomputed from the log.

### 3.5 AJAX Update Mechanism

Each HTML page loads a minimal JavaScript block that:
1. Calls `setInterval(fetchAndUpdate, 3000)` on page load.
2. `fetchAndUpdate()` issues a `fetch('/api/events')` (or `/api/active`) request.
3. On success, the response JSON is parsed and the table DOM is rebuilt in place.
4. On error (e.g. server temporarily unreachable), the existing table is kept and a status indicator is updated.

No external JavaScript frameworks are required — vanilla JS is sufficient.

### 3.6 Key Implementation Components

- **`HttpLoggingServer`** — creates a `ServerSocket` on port 8090, accepts connections in a loop, and spawns a `HttpRequestHandler` thread per request.
- **`HttpRequestHandler`** — parses the HTTP request line, routes to the correct handler method, and writes the HTTP response. Implements HTTP/1.0 (no keep-alive required).
- **`AccessLogStore`** — thread-safe in-memory store shared by both the UDP receiver (US090) and the HTTP server (US091). Provides `addEntry(AccessLogEntry)`, `getRecentEntries(int n)`, and `getActiveSessions()`.
- **`AccessLogEntry`** — immutable value object (from US090): `eventType`, `service`, `timestamp`, `username`, `clientIp`, `clientPort`. Serialises to JSON via a `toJson()` method.
- **`RemoteAccessesLoggingServer`** — main entry point. Starts UDP receiver thread (US090) and HTTP listener thread (US091), then blocks.

### 3.7 Threading Model

```
RemoteAccessesLoggingServer (main thread)
├── UdpReceiveLoop (thread) ──→ AccessLogStore.addEntry()
└── HttpLoggingServer (thread)
        └── HttpRequestHandler (one per request, daemon thread)
                └── AccessLogStore.getRecentEntries() / getActiveSessions()
```

All access to `AccessLogStore` is synchronised on the store's internal lock.

## 4. Integration/Demonstration

1. Start the **Remote Accesses Logging Server**:
   ```
   java -jar remote-logging-server.jar
   ```
   The server logs: `UDP listening on port 9090` and `HTTP listening on port 8090`.

2. Open a browser and navigate to `http://<server-host>:8090/` — the events page loads (initially empty).

3. Connect a Pilot client (US86), authenticate → `LOGIN_SUCCESS` entry appears in the browser within 3 seconds (AJAX update).

4. Navigate to `http://<server-host>:8090/active` — the active users page shows the logged-in pilot.

5. Logout from the Pilot client → the active users page removes the pilot within 3 seconds.

6. Force-close the Pilot client → a `DISCONNECT` entry appears in the events page; the pilot disappears from the active page.

7. Repeat with US44 and US78 clients to confirm all three services appear correctly on both pages.

## 5. Observations

- The HTTP server implements a minimal subset of HTTP/1.0 — only `GET` requests are needed. No cookies, no sessions, no TLS.
- AJAX polling at 3-second intervals is sufficient given the expected low event frequency. A shorter interval could be used if needed, at the cost of slightly higher CPU usage on the server.
- The in-memory log is bounded to the last **1000 entries** by default to prevent unbounded memory growth. The `/api/events` endpoint returns the last **50** by default; this can be adjusted via a query parameter (`?n=100`).
- The log file written to disk by the UDP receiver (US090) is separate from the in-memory store — it is append-only and not read back at startup. The in-memory store starts empty on each server restart.
- Port **8090** is used for HTTP and port **9090** for UDP. Both are configurable via command-line arguments.
