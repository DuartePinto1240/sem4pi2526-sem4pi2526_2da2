# US109 — Generate and Store Final Simulation Report

## 1. Context

This User Story is being developed in Sprint 3 as part of the **SCOMP** course unit.

US109 introduces the **report generation thread** — one of the four dedicated threads
spawned by the parent process (US106). It runs concurrently with the simulation, receives
real-time violation notifications via a condition variable (US107), and writes the
complete simulation report to a timestamped file at the end of the simulation.

The report infrastructure (`SimulationReport` struct, `ViolationEvent` struct,
`write_report()`, `print_report_summary()`, `make_report_filename()`) was implemented in
Sprint 2. US109 focuses on the **thread lifecycle** — how the report thread is started,
how it is notified, and when it writes the final report.

This US depends on **US100** (simulation framework), **US101** (position updates),
**US102** (violation detection), **US105** (shared memory), **US106** (thread creation),
and **US107** (condition variable notification).

## 3. Analysis

### 3.1 Domain Understanding

The simulation report consolidates all data accumulated during a run: individual flight
statuses, safety violation events with full positional and velocity data, and the final
pass/fail outcome. It is produced by a dedicated thread so as not to block the main
simulation loop.

The report is written to a plain-text file with a timestamped filename
(e.g. `simulation_report_20260615_143022.txt`) ensuring each run produces a unique file.

### 3.2 Thread Architecture

The parent process spawns four threads (US106):

```
Parent Process
    │
    ├── SimulationController thread  — drives the step loop
    ├── ViolationDetector thread     — detects violations, signals report thread
    ├── ReportGenerator thread       ← US109
    │       ├── waits on g_report_cond for violation notifications
    │       ├── accumulates violations in real time
    │       └── on g_sim_done=1: writes final report to file
    └── Environment thread (US110)   — updates wind data
```

### 3.3 Synchronisation

Two condition variable channels are used:

| Channel | Mutex | Condition | Purpose |
|---|---|---|---|
| Violation notification | `g_report_mutex` | `g_report_cond` | `ViolationDetector` → `ReportGenerator` |
| Simulation done | `g_done_mutex` | — | `g_sim_done = 1` flag, checked in loop condition |

The report thread waits on `g_report_cond`. When a violation is detected,
`ViolationDetector` signals the condition. The report thread wakes, logs the violation
count, and goes back to waiting. When `g_sim_done = 1`, the loop exits and the final
report is written.

---

## 4. Design

### 4.1 Design Decisions

- **Condition variable for real-time notification**: The report thread does not poll — it
  blocks on `pthread_cond_wait` and is woken only when the violation detector signals it.
  This is CPU-efficient and guarantees the report thread never misses a violation.
- **`g_sim_done` as the termination flag**: A volatile int visible to all threads. Set to
  1 by the parent after the simulation loop ends. The report thread's while condition
  `!g_sim_done` exits cleanly on the next wakeup.
- **`write_report()` called once at the end**: Violation data is accumulated in the
  `SimulationReport` struct during the simulation. The file write happens only once —
  after `g_sim_done = 1` — so the file is always a complete, consistent snapshot.
- **Timestamped filename**: `make_report_filename()` produces a unique filename per run
  so previous reports are never overwritten.

## 5. Implementation

### 5.1 Report Generation Thread — `simulation.c`

The thread is already implemented as `report_generator_thread` in `simulation.c`:

```c
static void *report_generator_thread(void *arg) {
    ThreadArgs *args = (ThreadArgs *)arg;
    printf("[RG] Report generator thread started (tid=%lu)\n",
           (unsigned long)pthread_self());

    pthread_mutex_lock(&g_report_mutex);

    while (!g_sim_done) {
        pthread_cond_wait(&g_report_cond, &g_report_mutex);

        if (args->report->total_violations > 0) {
            printf("[RG] Violation notification received — total so far: %d\n",
                   args->report->total_violations);
        }
    }

    pthread_mutex_unlock(&g_report_mutex);

    printf("[RG] Simulation done — writing final report\n");
    char report_fname[64];
    make_report_filename(report_fname, sizeof(report_fname));
    write_report(args->report, report_fname);
    print_report_summary(args->report);
    return NULL;
}
```

### 5.2 Report File Format — `report.c`

The `write_report()` function produces the following structure:

```
========================================
  AISafe Simulation Report
  Generated: Mon Jun 15 14:30:22 2026
========================================

--- Summary ---
Total flights    : 3
Total violations : 2
Result           : FAIL

--- Flight Statuses ---
Flight 0 : OK
Flight 1 : VIOLATED
Flight 2 : VIOLATED

--- Safety Violation Events ---

Violation #1
  Timestamp : 3.00 s
  Flight 1  : 1
    Lat=41.2481 Lon=-8.6814 Alt=10000.0
    Velocity : vx=0.0010 vy=0.0008 vz=0.0000
  Flight 2  : 2
    Lat=41.2490 Lon=-8.6800 Alt=10000.0
    Velocity : vx=-0.0010 vy=0.0008 vz=0.0000

========================================
  End of Report
========================================
```

### 5.3 Thread Spawning — `spawn_parent_threads()` in `simulation.c`

The report generator thread is created alongside the other three threads:

```c
pthread_create(&out_tids[2], NULL, report_generator_thread, thread_args);
```

  (`simulation_report_YYYYMMDD_HHMMSS.txt`) is created in the working directory.
- Open the file and verify:
    - Total flights matches the `num_flights` argument.
    - Individual flight statuses show which flights violated.
    - The Result is PASS if `total_violations < max_violations`, FAIL otherwise.
- Run with a very low threshold (e.g. `999999`) to force violations and verify that
  violation events appear with timestamps, positions, and velocity vectors.
- Run two simulations back-to-back and verify that two separate report files exist with
  different timestamps.

## 7. Observations

- The report generation thread is one of four threads defined in US106. The others are
  the simulation controller, violation detector, and environment thread (US110).
- The `write_report()` function in `report.c` is reused by the Java layer — the
  `SimulationReportController` in the EAPLI application reads the generated file and
  displays it in the Flight Control Operator menu.
- All shared memory reads by the report thread during final aggregation are protected by
  `pthread_mutex_lock(&g_shm_mutex)` to prevent data races with the violation detector
  thread.
- Report files must never be overwritten — the timestamped naming convention guarantees
  each run produces a unique file.
- US112 (Monthly Statistics Report) will aggregate data across multiple report files.
