# US078 — ATCC Collaborator Remote Access (EAPLI)

## 1. Context

This User Story was developed in Sprint 3. It introduces a remote access mechanism allowing Air Transport Company Collaborators (ATCC) to interact with the AISafe system from outside the main application, over a TCP network connection.

The ATCC is responsible for several core user stories — **US070** (Add Aircraft to Fleet), **US071** (Decommission Aircraft), **US072** (List Company Fleet), and **US073** (Create Flight Route) — which were previously only accessible through the local backoffice console. US078 makes all of them remotely available through a dedicated TCP client application, without any direct database access from the client side.

This US depends on all ATCC user stories being implemented and their controllers being available for delegation.

### 1.1 List of Issues

Analysis: Understand what constitutes a valid remote access session; identify which commands map to which ATCC user stories; define the text-based protocol.

Design: Design `ATCCServer`, `ATCCClientHandler`, `ATCCClient`, and `Protocol`; define command/response tokens; define session lifecycle.

Implement: Implement the server, handler, client, and protocol; bootstrap default users; enforce authentication before any command.

Test: Manual integration tests for all commands; authentication rejection; multi-line responses.

## 3. Analysis

### 3.1 Domain Understanding

The US078 TCP server acts as a **remote facade** over the existing EAPLI application layer. It does not introduce new domain entities — instead it exposes the existing controllers over a text-based TCP protocol. The key design constraint is that the client never accesses the database directly: all persistence operations happen server-side through the existing application-layer controllers.

Authentication uses the existing `AuthzRegistry` / `LoginController` infrastructure. The server bootstraps default ATCC users on startup so the service is usable even before the full backoffice bootstrap has run.

### 3.2 Session Lifecycle

```
Client connects
      │
      ▼
Awaiting LOGIN
      │
      ▼  (LOGIN email password)
Authentication check
      │
      ├── FAIL → ERROR Invalid credentials
      │
      └── SUCCESS → authenticated = true
                        │
                        ▼
              Commands accepted:
              LIST_AIRPORTS, LIST_MODELS,
              ADD_AIRCRAFT, LIST_FLEET,
              LIST_FLEET_MODEL, LIST_FLEET_MAKER,
              LIST_FLEET_CAP, LIST_FLEET_AGE,
              DECOMMISSION, CREATE_ROUTE
                        │
                        ▼  (LOGOUT)
              authenticated = false → BYE
```

### 3.3 Protocol Design

The protocol is text-based, one command per line. Arguments are space-separated. Multi-line responses are terminated by `END`.

**Commands:**

| Command | Arguments | Delegates to | Description |
|---|---|---|---|
| `LOGIN` | `<email> <password>` | `LoginController` | Authenticate as ATCC |
| `LIST_AIRPORTS` | — | `AirportRepository` | List all registered airports |
| `LIST_MODELS` | — | `AircraftModelRepository` | List all aircraft models |
| `ADD_AIRCRAFT` | `<reg> <country> <iata> <modelId> <eco> <bus> <first> <crew>` | `AddAircraftToFleetController` | Add aircraft to fleet (US070) |
| `LIST_FLEET` | `<iata>` | `ListCompanyFleetController` | List company fleet (US072) |
| `LIST_FLEET_MODEL` | `<iata> <modelId>` | `ListCompanyFleetController` | Filter fleet by model |
| `LIST_FLEET_MAKER` | `<iata> <maker>` | `ListCompanyFleetController` | Filter fleet by manufacturer |
| `LIST_FLEET_CAP` | `<iata> <minSeats>` | `ListCompanyFleetController` | Filter fleet by minimum seats |
| `LIST_FLEET_AGE` | `<iata>` | `ListCompanyFleetController` | List fleet ordered by age |
| `DECOMMISSION` | `<reg> <companyIata>` | `DecommissionAircraftController` | Decommission aircraft (US071) |
| `CREATE_ROUTE` | `<designator> <companyIata> <origin> <dest> REGULAR <day> <dep> <arr>` | `CreateFlightRouteController` | Create regular route (US073) |
| `CREATE_ROUTE` | `<designator> <companyIata> <origin> <dest> CHARTER <date1> <time1> <date2> <time2>` | `CreateFlightRouteController` | Create charter route (US073) |
| `LOGOUT` | — | `AuthzRegistry` | End the session |

**Response tokens:**

| Token | Meaning |
|---|---|
| `OK` | Command succeeded (single-line) |
| `OK <data>` | Command succeeded with result |
| `ERROR <reason>` | Command failed with explanation |
| `END` | Terminates a multi-line response |
| `BYE` | Server acknowledges logout and closes connection |

## 4. Design

### 4.1 Design Decisions

- **Separation of concerns**: `ATCCServer` only handles startup and connection acceptance. `ATCCClientHandler` handles the protocol and delegates to existing controllers. `ATCCClient` only handles user I/O and TCP communication.
- **No new domain logic**: US078 introduces no new domain entities or business rules — it is a pure infrastructure US that exposes existing application-layer functionality over TCP.
- **Authentication via existing framework**: `LoginController.login(email, password)` reuses the EAPLI `AuthzRegistry` — no custom authentication logic.
- **Bootstrap on startup**: `ATCCServer` bootstraps default ATCC users (and domain `User` records) on startup, making the service usable independently of the backoffice.
- **Multi-line responses terminated by END**: All list commands (airports, fleet, models) append `END` as the final line so the client knows when to stop reading.
- **Daemon threads**: Each client connection spawns a daemon thread — the server process does not wait for client threads to exit on shutdown.
- **PostgreSQL persistence unit**: The server uses `eapli.base.AlSafePU.postgres` to connect to the shared PostgreSQL instance at `vsgate-s1.dei.isep.ipp.pt:10466/alsafe`.

### 4.2 Class Diagram (CD)

Key classes involved:

```
ATCCClient  ──TCP──►  ATCCServer

                   ATCCClientHandler (Runnable)
```

## 5. Implementation

**`rcomp/Protocol.java`**
- Constants for all command and response tokens: `LOGIN`, `LOGOUT`, `ADD_AIRCRAFT`, `LIST_FLEET`, `LIST_FLEET_MODEL`, `LIST_FLEET_MAKER`, `LIST_FLEET_CAP`, `LIST_FLEET_AGE`, `DECOMMISSION`, `CREATE_ROUTE`, `LIST_AIRPORTS`, `LIST_MODELS`, `OK`, `ERROR`, `END`, `BYE`.

**`rcomp/ATCCServer.java`**
- Registers valid email domains (`alsafe.com`, `alsafe.pt`, `isep.ipp.pt`).
- Configures `AuthzRegistry` with `JpaAutoTxUserRepository`, `AlSafePasswordPolicy`, `PlainTextEncoder`.
- Bootstraps default ATCC and admin system users and domain `User` records (idempotent).
- Accepts TCP connections on port 2225 in an infinite loop; spawns daemon `ATCCClientHandler` thread per connection.

**`rcomp/ATCCClientHandler.java`**
- Implements `Runnable`; manages one client session.
- `authenticated` flag — gates all commands except `LOGIN`.
- `handle(line)` — dispatches command string to handler methods.
- Handler methods: `handleLogin`, `handleLogout`, `handleListAirports`, `handleListModels`, `handleAddAircraft`, `handleListFleet`, `handleListFleetByModel`, `handleListFleetByMaker`, `handleListFleetByCap`, `handleListFleetByAge`, `handleDecommission`, `handleCreateRoute`.
- Multi-line responses built with `StringBuilder` and terminated with `END`.
- All exceptions caught and returned as `ERROR <message>`.

**`rcomp/ATCCClient.java`**
- Connects to server via `Socket`.
- Reads user input in a loop and sends to server.
- Reads response until `OK`, `ERROR`, `BYE`, or `END` line detected.
- Disconnects on `BYE`.

**Persistence**
- No new tables introduced by US078.
- Uses existing `AIRCRAFT`, `FLIGHT_ROUTE`, `SYSTEM_USER`, `USER` tables via the existing controllers.

## 6. Integration/Demonstration

1. Start the **ATCCServer** in IntelliJ (`rcomp.ATCCServer`).
2. Start the **ATCCClient** in a second IntelliJ run configuration (`rcomp.ATCCClient`).
3. Test unauthenticated command → `LIST_AIRPORTS` → `ERROR Not authenticated`.
4. Authenticate → `LOGIN atcc@alsafe.com Atcc1234` → `OK Welcome atcc@alsafe.com`.
5. List airports → `LIST_AIRPORTS` → airport lines terminated by `END`.
6. List models → `LIST_MODELS` → model lines terminated by `END`.
7. Add aircraft → `ADD_AIRCRAFT CS-TCP Portugal TP 1 200 20 0 8` → `OK CS-TCP`.
8. List fleet → `LIST_FLEET TP` → aircraft lines terminated by `END`.
9. Filter by maker → `LIST_FLEET_MAKER TP Boeing` → filtered lines terminated by `END`.
10. Create regular route → `CREATE_ROUTE TP001 TP OPO LIS REGULAR MONDAY 14:00 15:00` → `OK TP001`.
11. Create charter route → `CREATE_ROUTE TP002 TP OPO CDG CHARTER 2026-06-15 10:00 2026-06-15 13:00` → `OK TP002`.
12. Decommission → `DECOMMISSION CS-TCP TP` → `OK CS-TCP decommissioned`.
13. Logout → `LOGOUT` → `BYE`.

## 7. Observations

- Port **2225** is dedicated to the ATCC service. The Weather Person server (US044) uses port 2226 and the Pilot server (US086) uses port 2228.
- The server uses persistence unit `eapli.base.AlSafePU.postgres` connecting to `vsgate-s1.dei.isep.ipp.pt:10466/alsafe`. The client has no database access — all persistence is done server-side.
- The bootstrap in `ATCCServer` is idempotent — existing users cause a caught exception that is silently ignored.
- `ValidEmailDomains` must be registered before `AuthzRegistry.configure()` for authentication to work correctly during the bootstrap phase.
- `DECOMMISSION` requires both the registration number and the company IATA as arguments, matching the signature of `DecommissionAircraftController.decommissionAircraft(reg, companyIata)`.
- `CREATE_ROUTE` with `CHARTER` type requires 9 arguments: `designator companyIata origin dest CHARTER date1 time1 date2 time2`. Date format is `yyyy-MM-dd` and time format is `HH:mm`.
