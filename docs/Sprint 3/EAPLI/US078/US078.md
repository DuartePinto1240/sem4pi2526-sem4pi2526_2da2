# US078 - Air Transport Company Collaborator Remote Access

## 1. Context

This User Story is being developed for the first time in Sprint 3. It allows an Air Transport Company Collaborator to remotely access the system using a dedicated TCP-based client application. All Air Transport Company Collaborator user stories must be available through this remote client.

This US depends on US030 (authentication and authorization), US061 (add a collaborator), and all Air Transport Company Collaborator user stories (US070–US077), as these are the functionalities that must be remotely accessible.

## 3. Analysis

### 3.1 Domain Understanding

Remote access introduces a **client-server split**: the existing application logic (controllers, domain, repositories) runs on the **server side**, embedded in the system. A dedicated **client application** connects to the server over TCP and provides the same interface that the local console UI provides.

The critical constraint is that the client must never interact with the database directly — all data access must go through the server's application layer.

### 3.2 Communication Architecture

| Layer | Component | Responsibility |
|---|---|---|
| Client | `AirTransportCompanyApp` | TCP client — user interaction, send requests, display responses |
| Network | TCP socket | Reliable, ordered byte stream between client and server |
| Server | Embedded TCP server | Accept connections, deserialize requests, delegate to controllers, serialize responses |
| Application | Existing controllers (US070–US077) | Business logic — unchanged from local use |

### 3.3 Key Business Rules

- Every request must carry authentication credentials — verified by the server before any controller is invoked.
- The client must not hold or cache any business data beyond what is needed for the current interaction.
- All existing authorization rules (role checks) are enforced on the server side, not the client side.

## 4. Design

### 4.1 Design Decisions

- **TCP over UDP**: TCP is chosen because it provides reliable, ordered delivery, which is required for request-response interactions where the client needs a guaranteed reply.
- **Reuse existing controllers**: The server side reuses the existing controller classes unchanged. The TCP server is an additional presentation layer that delegates to the same application layer used by the console UI.
- **Message-based protocol**: Requests and responses are serialized as structured messages (e.g., JSON or a custom binary format) to decouple the client from the server's internal representation.
- **Authentication per connection**: The client authenticates once when establishing the connection. The server stores the session context for the duration of the connection.
- **No direct DB access from client**: The client only sends requests and receives responses — it has no knowledge of the database schema or location.

### 4.3 Sequence Diagram (SD)

*to be added*

The high-level flow is:

1. Collaborator starts the client application and provides credentials.
2. Client establishes a TCP connection to the server and sends an authentication request.
3. Server validates credentials — closes connection if invalid.
4. Collaborator selects an operation (e.g., add aircraft, list fleet).
5. Client serializes the request and sends it over TCP.
6. Server deserializes the request, checks authorization, and delegates to the appropriate controller.
7. Server serializes the response and sends it back.
8. Client displays the result to the collaborator.

**Test 3:** An unauthenticated request is rejected by the server.

**Refers to Acceptance Criteria:** US078.4

    assertEquals(ResponseCode.UNAUTHORIZED, response.code());
    client.disconnect();
}

## 5. Implementation

Key implementation notes:
- The TCP server runs on a dedicated thread within the system process and listens on a configured port.
- Each client connection is handled by a separate thread to support concurrent collaborators.
- Authentication on the server side uses the same `AuthorizationService` as the local console application.
- The server enforces `authz.ensureAuthenticatedUserHasAnyOf(BaseRoles.AIR_TRANSPORT_COMPANY_COLLABORATOR)` for every operation, just as the local controllers do.
- The client application is a separate runnable (separate `main` class) that communicates exclusively via TCP.

## 7. Observations

- The TCP server must be started as part of the system bootstrap process so it is available immediately on system startup.
- The port number used by the server should be configurable (e.g., via a properties file) to avoid conflicts.
- All Air Transport Company Collaborator user stories (US070–US077) must be supported by the remote client. If a new US is added in a future sprint for this role, it must also be made available remotely.
