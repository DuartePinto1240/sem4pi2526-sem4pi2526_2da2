# US081 — Create a Flight Plan from a File

## 1. Context

This User Story is being developed for the first time in Sprint 2. It is part of the **LPROG** course unit and is mandatory for all students enrolled in it.

US081 introduces the ability for a Pilot to create a flight plan by importing a file written in the **Core Flight DSL** — a Domain Specific Language defined specifically for the AISafe system. The file is validated through lexical, syntactic and semantic analysis before being accepted by the system.

This US directly depends on **US083** (Flight DSL Specification and Validation), which defines the grammar and the ANTLR-based processing pipeline that US081 uses.

## 2. Requirements

**US081** As a Pilot, I want to create a flight plan from a file.

> There may be multiple file formats, and I want to validate the file format before using it.

**Acceptance Criteria:**

- US081.1 — The flight plan file must conform to the Core Flight DSL.
- US081.2 — The file must be validated through **lexical**, **syntactic** and **semantic** analysis before being accepted.
- US081.3 — Invalid files must produce **meaningful error messages**, including the type of error, and the line and column where it occurred.
- US081.4 — Only valid flight plans may be imported and used by the system.
- US081.5 — The system must use **at least one ANTLR visitor and one ANTLR listener** in the processing pipeline.

**Dependencies/References:**

- **US083** — defines the Core Flight DSL grammar (ANTLR); US081 reuses this grammar directly.
- **US080** — flight plans created from files follow the same domain model as manually created plans.
- Referenced in the specification, sections 3.4.1 – 3.4.5.

## 3. Analysis

### 3.1 Core Flight DSL — Structure

A flight plan file is hierarchical and block-based. Its top-level structure is:

```
flight <ID> {
    type: <regular | charter>

    leg {
        departure: <AIRPORT_CODE> <DATE> <TIME>
        arrival:   <AIRPORT_CODE> <TIME>
        fuel:      <QUANTITY> <UNIT>

        segment {
            from: (<lat>, <lon>)
            to:   (<lat>, <lon>)
            altitude_slots: [<alt1>, <alt2>, ...]
            width: <value> m
            wind:  <angle> deg <speed> m/s
        }
        // one or more segments
    }
    // one or more legs
}
```

Key lexical elements:
- **Keywords** (case-insensitive): `flight`, `leg`, `departure`, `arrival`, `route`, `segment`, `fuel`
- **Identifiers** (case-sensitive): flight IDs, named entities
- **Airport codes**: IATA (3 letters) or ICAO (4 letters)
- **Numeric literals**: integers and floating-point
- **Date/time literals**: departure dates and times
- **Units**: `kg`, `l`, `m`, `m/s`
- **Separators**: `{ }`, `( )`, `[ ]`, `,`, `:`, `;`

### 3.2 Validation Pipeline

The file goes through three sequential validation phases:

```
File Input
    │
    ▼
┌─────────────┐
│  Lexical    │  ANTLR Lexer — tokenises the input;
│  Analysis   │  detects unknown tokens and illegal characters.
└──────┬──────┘
       │ token stream
       ▼
┌─────────────┐
│  Syntactic  │  ANTLR Parser — checks structural correctness;
│  Analysis   │  verifies blocks, nesting and mandatory fields.
└──────┬──────┘
       │ parse tree
       ▼
┌─────────────┐
│  Semantic   │  Visitor/Listener — checks domain coherence:
│  Validation │  unique IDs, airport code formats, positive values,
└──────┬──────┘  leg sequence, route coherence, etc.
       │
       ▼
  Internal representation (domain objects)
  → flight plan is accepted and created in the system
```

### 3.3 Semantic Validation Rules (section 3.4.5)

**Flight level:**
- Flight identifier must be unique within the file.
- Flight type must be `regular` or `charter`.

**Leg level:**
- Each leg must have exactly one departure and one arrival.
- Each leg must have at least one segment.
- Fuel quantity must be strictly positive.

**Leg sequence coherence:**
- Arrival airport of leg *n* must match departure airport of leg *n+1*.
- Arrival time of leg *n* must precede departure time of leg *n+1*.

**Route coherence:**
- Route origin must match the first leg's departure airport.
- Route destination must match the last leg's arrival airport.
- The same airport cannot be visited twice.

**Segment coherence:**
- Start and end coordinates must be different.
- Segments belong to exactly one leg.

**Domain consistency:**
- Airport codes must respect IATA (3 letters) or ICAO (4 letters) format.
- Numeric values (altitudes, widths, wind speed, fuel) must be positive.
- Date and time values must be valid calendar values.

> All semantic errors are **collected and reported in a single execution** — the system does not stop at the first error.

## 4. Design

### 4.1 Design Decisions

- **ANTLR4** is used to define the grammar (`FlightPlan.g4`) and generate the lexer, parser, visitor base and listener base.
- **At least one Listener** is used (e.g., for collecting structural elements during tree traversal).
- **At least one Visitor** is used (e.g., for semantic validation, returning typed results per node).
- **Domain objects** are built from the parse tree — the system does not use a separate AST; it populates flight plan domain entities directly.
- **Error collection**: a custom `ErrorCollector` accumulates all errors from all three phases; no early exit on first error.

### 4.2 ANTLR Component Overview

| Component | Role |
|---|---|
| `FlightPlan.g4` | Grammar file — defines lexer and parser rules |
| `FlightPlanLexer` | Generated — tokenises the input stream |
| `FlightPlanParser` | Generated — builds the parse tree |
| `FlightPlanListener` | Listener interface (generated) + custom implementation |
| `FlightPlanVisitor` | Visitor interface (generated) + custom implementation for semantic validation |
| `ErrorCollector` | Accumulates lexical, syntactic and semantic errors |
| `FlightPlanImporter` | Orchestrates the pipeline; returns domain objects or error list |

### 4.3 Error Reporting

Each error includes:
- **Type**: Lexical / Syntactic / Semantic
- **Line** and **column** where the error was found
- **Description**: human-readable message explaining what is wrong

Example output:
```
[LEXICAL]   Line 3, Col 12 — Unknown token '#'
[SYNTACTIC] Line 7, Col 1  — Missing 'arrival' block in leg
[SEMANTIC]  Line 14, Col 8 — Fuel quantity must be positive (got: -500)
[SEMANTIC]  Line 21, Col 4 — Airport 'LPPT' visited twice in flight
```

## 5. Implementation

### 5.1 Grammar (`FlightPlan.g4`)

The grammar is defined in ANTLR4 format and placed in the `src/main/antlr4` directory. It is compiled by the Maven ANTLR plugin to generate the lexer, parser, visitor and listener Java sources automatically.

Key grammar rules:
- `flightPlan` — top-level rule; one or more `flight` blocks.
- `flight` — contains an ID, type, and one or more `leg` blocks.
- `leg` — contains `departure`, `arrival`, `fuel`, and one or more `segment` blocks.
- `segment` — contains coordinate pairs, altitude slots, width and wind.

### 5.2 Processing Pipeline (`FlightPlanImporter`)

```java
public FlightPlanImportResult importFromFile(String filePath) {
    // 1. Lexical analysis
    CharStream input = CharStreams.fromFileName(filePath);
    FlightPlanLexer lexer = new FlightPlanLexer(input);
    lexer.addErrorListener(errorCollector);

    // 2. Syntactic analysis
    CommonTokenStream tokens = new CommonTokenStream(lexer);
    FlightPlanParser parser = new FlightPlanParser(tokens);
    parser.addErrorListener(errorCollector);
    ParseTree tree = parser.flightPlan();

    if (errorCollector.hasErrors()) {
        return FlightPlanImportResult.failure(errorCollector.getErrors());
    }

    // 3. Semantic validation via Visitor
    FlightPlanSemanticVisitor visitor = new FlightPlanSemanticVisitor(errorCollector);
    visitor.visit(tree);

    if (errorCollector.hasErrors()) {
        return FlightPlanImportResult.failure(errorCollector.getErrors());
    }

    // 4. Build domain objects via Listener
    FlightPlanBuilderListener builder = new FlightPlanBuilderListener();
    ParseTreeWalker.DEFAULT.walk(builder, tree);
    return FlightPlanImportResult.success(builder.getFlightPlan());
}
```

### 5.3 Visitor — Semantic Validation

The `FlightPlanSemanticVisitor` extends the generated `FlightPlanBaseVisitor<Void>`. It overrides `visit*` methods for each rule node where semantic checks are needed:

- `visitFlight()` — checks unique flight ID, valid type.
- `visitLeg()` — checks exactly one departure, one arrival, at least one segment, positive fuel.
- `visitSegment()` — checks start ≠ end coordinates, positive numeric values.
- `visitAirportCode()` — validates IATA/ICAO format with regex.

### 5.4 Listener — Domain Object Builder

The `FlightPlanBuilderListener` extends the generated `FlightPlanBaseListener`. It uses `enterFlight()`, `exitFlight()`, `enterLeg()`, `exitLeg()`, etc. to progressively build the domain `FlightPlan` object as the tree is walked.

## 6. Integration/Demonstration

1. The Pilot selects the option to create a flight plan from a file.
2. The system prompts for the file path.
3. The file is processed through the three-phase validation pipeline.
4. **If valid**: the flight plan is created in the system and confirmed to the Pilot.
5. **If invalid**: all errors are displayed with their type, line and column. The flight plan is **not** created.

**Example — valid file accepted:**
```
>> Flight plan imported successfully.
   Flight ID : TP001
   Type      : regular
   Legs      : 2
   Status    : DRAFT
```

**Example — invalid file rejected:**
```
>> Flight plan file is invalid. The following errors were found:

   [SYNTACTIC] Line 5, Col 1  — Missing 'fuel' block in leg
   [SEMANTIC]  Line 12, Col 8 — Fuel quantity must be positive (got: 0)
   [SEMANTIC]  Line 19, Col 4 — Departure airport of leg 2 ('LPPR') does not
                                 match arrival airport of leg 1 ('LPPT')

>> Flight plan was NOT created.
```

## 7. Observations

- The grammar file (`FlightPlan.g4`) is shared between US081 and US083. US083 is responsible for defining and documenting the grammar; US081 consumes it.
- Keywords are **case-insensitive** as per the specification. Identifiers and literals are **case-sensitive**.
- The DSL is designed to be extensible: new keywords, constructs or validation rules can be added without breaking existing valid files (backward compatibility requirement).
- The implementation language is **Java** as required by the specification (section 3.4.4, point 7).
- Semantic errors are all collected before reporting (no fail-fast), as required by section 3.4.5: *"All semantic errors must be collected and reported in a single execution."*
